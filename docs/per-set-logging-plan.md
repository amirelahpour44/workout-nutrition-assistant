# پلن: ثبت ست‌به‌ست تمرین (وزنه و تکرار مستقل برای هر ست)

> **وضعیت: پیاده‌سازی کامل شد (فاز ۱، ۲ و ۳).** عنوان‌های ✅ = انجام‌شده؛ تست‌ها: ۴۳/۴۳ پاس + تست مرورگر دستی (تایپ ست، افزودن/حذف، ثبت سریع، رکورد، stale، بکاپ قدیمی، reload، هدف ست‌به‌ست در برنامه).

## مسئله
الان هر حرکت فقط یک رکورد تجمعی `{ w, r, s }` (وزنه، تکرار، ست) در هفته دارد. یعنی سناریوی رایج «۳ ست که دوتای اول ۸ تکرار و سومی ۶ تکراره» اصلاً قابل ثبت نیست. راه‌حل نباید صفحه ترکر را برای همه حرکت‌ها شلوغ کند — اکثر حرکت‌ها همه ست‌هایشان یکسان است.

## تصمیم‌های گرفته‌شده
1. **UX ترکیبی:** حالت پیش‌فرض = ردیف فشرده فعلی + چیپ خلاصه؛ با تپ، به‌صورت inline باز می‌شود و لیست ست‌به‌ست می‌دهد. هر ست جدید از ست قبلی پیش‌پر می‌شود.
2. **وزنه مستقل برای هر ست** (حالت پیرامیدی ۴۰/۴۵/۵۰ پشتیبانی می‌شود).
3. **بونوس فاز ۳:** ثبت سریع متنی با فرمت `8/8/6` یا `3×8` (اعداد فارسی و انگلیسی).

## ✅ فاز ۱ — دیتا مدل و مهاجرت (پایه، بدون تغییر UI)

### شکل جدید رکورد
```
جدید:  logs[weekKey][exId] = { sets: [ { w: 40, r: 8 }, { w: 40, r: 8 }, { w: 40, r: 6 } ] }
قدیمی: logs[weekKey][exId] = { w: 40, r: 8, s: 3 }   // پذیرفته می‌شود
```
- `w` برای هر ست اختیاری است (حرکات وزن بدن).
- `r` از ۰ به بالا (برای ست ناتمام هم قابل قبول)، `w` از ۰ با step فعلی ۰.۲۵.

### توابع جدید (app.js)
- `normalizeLogRec(rec)` — اگر `rec.sets` آرایه معتبر نیست ولی `w/r/s` دارد، تبدیل به `sets` می‌کند (`s` بار `{w, r}` یکسان). خروجی همیشه شکل جدید.
- `logSets(rec)` — خواندن امن: `normalizeLogRec(rec).sets` (همیشه آرایه، شاید خالی).
- `aggregateLog(rec)` → `{ w: بیشینهٔ وزنه‌ها, r: بیشینهٔ تکرارها, s: تعداد ست‌ها }` — برای سازگاری با نمایش‌ها و stale.

### نقاط نرمال‌سازی (همه مسیرهای ورود داده)
- `loadSection` / init برای `wna_logs_v1` (حدود خط ۱۳۹۶ و ۱۴۰۹).
- `restoreBackup` بعد از اعتبارسنجی (حدود خط ۱۳۱۵).
- فرمت بکاپ JSON تغییر نمی‌کند؛ `validLogs` همین‌طور ساده می‌ماند چون نرمال‌سازی در خواندن انجام می‌شود (هر دو شکل برای همیشه خوانده می‌شوند).

### منطق رکورد (PR) — هماهنگ با دیتای ست‌به‌ست ✅
- `getPersonalRecord(exId, field, ...)`: امضای تابع ثابت، ولی حالا از `logSets` می‌خواند:
  - `field='w'` → بهترین وزنه در بین همه ست‌های همه هفته‌ها
  - `field='r'` → بهترین تکرار در بین ست‌ها
  - `field='s'` → بیشترین تعداد ست ثبت‌شده در یک هفته
- **هایلایت رکورد ست‌به‌ست:** فقط اینپوت «ستِ» رکوردزن کلاس `is-pr` می‌گیرد (مثلاً در ثبت سریع `3×8@42.5` هر سه وزنه پررنگ طلایی می‌شوند)؛ تروفه بالای حرکت وقتی هر ست رکورد زده باشد.
- `isNewRecord` بدون تغییر (`value > priorBest`؛ برابر شدن رکورد نمی‌شکند).
- `isStaleNum` **فعلاً عمیق**: مقایسه ترجمه ست‌به‌ست کامل این هفته با هفته قبل (`isStaleLogTrace`) — همان ۸/۸/۶ با همان وزنه‌ها = stale، ولی ۸/۸/۶ در برابر ۸/۸/۸ = نه stale (پیشرفت سقوط کرده، عین تکرار نیست). رکوردهای قدیمی `{w,r,s}` بعد از نرمال‌سازی دقیقاً مثل قبل مقایسه می‌شوند.
- `exerciseHasPrThisWeek` جدید: منبع واحد تروفه (برای حالت جمع‌شده و باز).
- در حالت ویرایش باز، placeholder هر ست از همان ایندکسِ هفته قبل می‌آید و بعدش از رکورد شخصی — پس «ضربان رکورد» خودش را نشان می‌دهد.

**تحویل فاز ۱:** رکوردهای قدیمی عیناً کار می‌کنند، PRها و هفته‌قبل‌ها حفظ می‌شوند، هنوز UI سه‌سلولی است.

## ✅ فاز ۲ — UI چیپ خلاصه + ویرایش inline

### حالت جمع‌شده (پیش‌فرض — صفحه همچنان خلوت)
`buildTrackRowHtml` بازنویسی می‌شود:
```
پرس سینه 🏆                          ⌄
هفته قبل: ۴۰ کیلو • ۸/۸/۶
[ ست‌ها: ۸/۸/۶ • ۴۰ کیلو ]        ← چیپ/دکمه باز کردن
```
- چیپ خلاصه: توزیع تکرارها `۸/۸/۶` (با faNum) + خلاصه وزنه (یکی برای همه، یا `۴۰/۴۵/۵۰`).
- اگر خالی: placeholder هدف از برنامه `هدف: ۳×۸`.
- عناصر فعلی که می‌مانند: trophy، نکته فنی، prev-hint، is-stale.
- سلول‌های سه‌گانه `w/r/s` حذف و با چیپ جایگزین می‌شوند.

### حالت باز (accordion — همیشه فقط یک حرکت باز)
```
┌──────────┬──────────────┬──────────┬───┐
│ ست       │ وزنه (کیلوگرم) │ تکرار    │ ✕ │
├──────────┼──────────────┼──────────┼───┤
│ ۱        │ ۴۰           │ ۸        │   │
│ ۲        │ ۴۰           │ ۸        │   │
│ ۳        │ ۴۰           │ ۶        │   │
└──────────┴──────────────┴──────────┴───┘
[＋ افزودن ست]  [⧉ کپی از هفته قبل]
```
- `＋ افزودن ست`: ست جدید پیش‌پر شده از آخرین ست → بعد از آن `{ w: هفته قبل یا آخرین رکورد, r: ex.reps }`.
- «کپی از هفته قبل»: جایگزینی کل ست‌ها با `logSets(prev)`.
- حداکثر ۱۲ ست؛ حذف آخرین ست مجاز نیست (یا رکورد خالی می‌شود).
- ورودی‌ها با `data-wk / data-ex / data-set="index" / data-field="w|r"` — همان الگوی handler فعلی `input` در `#panel-tracker` (خط ۱۴۴۹) توسعه می‌یابد و با `queueLogsSave` ذخیره می‌شود.
- state.ui جدید: `expandedTrackExId: null` (فقط session، ذخیره نمی‌شود).
- `updateRowHighlights` برای ردیف باز هم کار کند (is-pr روی اینپوت ستِ رکوردزن).

### ساختار کد
- `buildTrackRowHtml` (خط ۶۳۵) → دو تابع: `buildTrackCollapsedHtml` + `buildTrackExpandedHtml`.
- رویداد toggle در delegation کلیکِ document (خط ۱۴۱۷): `data-action="toggle-track-set"`.
- `styles.css`: `.track-sets`, `.set-row`, `.chip-sets`, انیمیشن باز شدن، حالت is-pr/is-stale روی ست‌ها.

## فاز ۳ — بونوس‌ها (همه ✅)

1. **✅ ثبت سریع متنی:** در داخل نمای باز، یک اینپوت با قبولی `8/8/6`، `3×8`، `2×8@40/1×6@45` (اعلام فارسی هم توسط `enNum`)، مجاز تا ۱۲ ست، خطا ⇒ toast و داده دست‌نخورده.
2. **✅ کپی از هفته قبل:** دکمه در نمای باز؛ جایگزینی کل ست‌ها با ترجمه هفته قبل.
3. **✅ هدف ست‌به‌ست در برنامه‌سازی:** فیلد متنی اختیاری «هدف ست‌به‌ست» در فرم ویرایش حرکت (همان گرامر پارسر، `targetsText` برای سریالایز رفت‌وبرگشتی). ذخیره ⇒ `ex.targets` پر و `ex.sets/ex.reps` همگام می‌شوند؛ خالی ⇒ هدف یکنواخت مثل قبل. اثر: متای کارت برنامه، چیپ خالی ترکر، و placeholderهای ست‌به‌ست (وزنه/تکرار هر ایندکس). فرمت غلط ⇒ toast و خارج نشدن از حالت ویرایش.
